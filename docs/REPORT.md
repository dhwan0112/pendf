## 0.8.0 — 보기 안 패널, 여백, 영역 발췌, 볼트 색인

### 1. 페이지 밖 좌표 점검 (INVESTIGATION §13)
- geometry, 사이드카 검증, 병합, 지우개 히트 테스트, 링크 형식·이동 어디에도 페이지 밖 좌표를 자르거나 거부하는 곳이 없었다(단위 시험 13개: 회전 4종 × MediaBox·CropBox 왕복 오차 1e-9 이내).
- 막는 것은 입력 판정 하나였다: 필기 시작·지우개·메모 놓기는 포인터 아래에 쪽 요소(`.page`)가 있어야 한다. 획이 쪽 경계를 넘는 것은 자르지 않는다. 줌 합성 변형(D-38)은 쪽 div 전체에 걸리므로 상자 밖 레이어도 함께 움직인다.
- 그래서 여백을 **쪽 요소의 일부**(테두리)로 만들었고, 데이터·입력 코드는 고치지 않았다.

### 2. 왼쪽 패널과 툴바 (D-42, D-43)
- 다섯 탭을 공용 컴포넌트(`src/panel/tabs.ts`, `registerPanelTab`)로 분리해 사이드바와 보기 안 패널이 같은 코드를 쓴다. 노트북·카드는 탭을 등록해 들어오면 된다.
- 보기 너비 ≥ 패널 + 560 px이면 고정, 아니면 겹침(바깥 탭으로 닫힘). 가장자리 스와이프는 쓰지 않는다. 열림·탭·너비·핀은 보기 상태.
- 위치 유지(하네스): 고정 패널 열기 0.38 px, 너비 변경 0.25 px, 닫기 0 px 어긋남(배율 117% → 84% → 117%). 썸네일 300칸 중 보이는 14개만 그림, 0.82 MB, 끝까지 스크롤 후 40쪽 해제. 썸네일은 캔버스 예산(D-39)에 들어간다.
- 툴바: 버튼 16개 모두 이름(aria-label·툴팁), 길게 누르면 이름, 360 px에서 9개가 More로 넘어가고 메모·필기·실행 취소·패널은 남는다.

### 3. 여백·영역 구현과 수치 (D-41, D-44)
- **여백:** 쪽 div 테두리를 여백 쪽으로 넓힌다(비율 × 쪽 고유 너비). 텍스트 레이어가 캔버스와 그대로 맞고, 여백 75%에서 하이라이트 정답 끝 오차 0.45 pt(CropBox 0.89 pt, 기준 3 pt). 여백 안 Pencil 획이 쪽 밖 좌표(x ≥ 654.8 pt, 쪽 595 pt)로 저장되고 여백에 그려짐; 여백 안 점 기준 줌 커밋 0.45 px, 획 위치 변화 0. 끄면 잘리고 쪽 가장자리 표식, 다시 열면 자동으로 켜짐. 메모 만들기·누르기·Move(탭)·실행 취소·삭제.
- **300쪽 PDF, 여백 50% + 고정 패널:** 5곳 이동 동안 쪽 캔버스 최대 10개, 최대 10 MB(데스크톱 DPR 1). 여백은 캔버스를 만들지 않는다.
- **영역:** `areas.pdf`(회전 4종 + CropBox)의 기준 사각형을 Pencil·손가락으로 끌어 만든 quad 오차 **0 pt**(5쪽 모두), 텍스트 "Figure N". 2× 이미지가 기준 사각형 색을 포함하고 주변이 흰색(픽셀), 크기 정확. 저장(첨부 파일 위치)·클립보드 복사(데스크톱)·패널 썸네일 5/5. 링크로 열면 그 쪽에서 깜박임. WebKit·Chromium에서도 5/5.

### 4. 호환성 왕복 결과 (D-44)
- 0.7.3 파서 사본(`tests/compat/v073`)으로: 0.8.0 사이드카(영역, `annotation` 메모, 새·옛 형식 하이라이트 메모)를 0.7.3이 읽으면 모르는 항목은 `unknown`에 들어가고, 0.7.3이 저장·동기 병합해도 그대로 남는다. 0.8.0이 다시 읽으면 **잃은 것 없이** 모두 주석으로 돌아온다(이를 위해 0.8.0 파서가 `unknown` 안의 검증되는 항목을 되돌린다; 같은 id는 병합 규칙). → **schemaVersion은 1 유지.**

### 5. 색인 성능 (D-45)
- 실제 테스트 볼트, 합성 사이드카 500개·주석 50,000개: 처음 구축 94 ms(파일 501개 읽기 포함), 메인 스레드 최장 조각 12.6 ms(6조각), 캐시로 다시 시작 56 ms(다시 읽기 0), 사이드카 하나 수정 → 반영 387 ms(그중 300 ms 모으기), 검색 52 ms. 이름 바꾸기·복사본·검색 명령으로 열기 하네스 통과.

## 0.7.2 — 핀치 줌의 검은 번쩍임과 끊김

측정은 모두 하네스 `zoom-gesture`(테스트 볼트, `long-300.pdf` 5쪽, 합성 두 손가락 터치·Ctrl+휠, 데스크톱 Obsidian/Chromium)다. ### 2. 설계 변경 (D-38, D-39)
1. 제스처 중에는 `.pdfViewer`의 CSS transform만 바꾼다. pdf.js 호출·레이아웃 읽기·레이어 작업 없음. 배율과 미리보기 위치는 커밋 뒤 닿을 수 있는 범위로 묶는다.
2. 손을 떼면 한 작업 안에서: transform 제거 → 배율 한 번 → pdf.js의 동기 `scalechanging` 안에서 손가락 아래 점을 맞추는 스크롤과 화면 밖 캔버스 해제 → 레이어 동기화. 커밋 뒤 pdf.js가 쪽 상자를 픽셀 격자에 맞추며 생기는 몇 px는 그 쪽이 그려질 때 다시 맞춘다.
3. 옛 캔버스는 새 캔버스가 완성될 때까지 남는다(재렌더가 취소돼도, 빌드 변환 규칙). 캔버스 아래 종이색 배경.
4. 캔버스 메모리: 프리셋(Default / Memory saver / No detail canvas / pdf.js defaults)과 예산.
5. 데스크톱: 트랙패드 핀치는 연속 합성, 휠 한 칸은 10% 한 단계(포인터 고정).
6. 계측: HUD(`canvasMB`, `zoomPreset`, `lastZoom`), 로그 요약, 명령 *Export last zoom timeline to vault*(프레임 간격, 렌더, 캔버스 생성·해제, 메모리 피크, 기준점 오차), 진단 모드의 빈·검은 캔버스 표본.

### 4. 기본 프리셋: Default (잠정)
- 쪽 캔버스 상한을 pdf.js 자신의 iOS 값(5,242,880 px)으로 되돌렸다. 0.7.1의 2^23은 이보다 60% 크다. iPad DPR 2의 쪽 폭 맞춤이 대략 이 값이고, 더 확대하면 pdf.js의 상세 캔버스(보이는 부분만)가 선명도를 맡는다.
- 상세 캔버스를 켜 둔다(끄면 확대 시 흐림. 메모리도 줄지 않았다: 60.2 MB).
- 화면 밖 캔버스 해제와 160 MB 예산을 더했다: 같은 상한에서 pdf.js 혼자일 때보다 피크가 낮다(47.9 vs 65.0 MB).
- 검은 화면이 iOS 메모리 때문인지는 데스크톱에서 가릴 수 없으므로, iPad 비교(DEVICE_CHECKLIST 7-3) 뒤 확정한다. 그때 앱이 꺼지거나 검게 번쩍이면 *Memory saver*가 후보다.
- **원인 판정(0.7.3, D-40):** 진단용 프리셋 *0.7.1 canvas cap*(모바일 2^23 px, 예산 없음, 커밋 때 해제 없음, 나머지 수정은 그대로)과 *Default*를 iPad에서 비교한다(DEVICE_CHECKLIST 7-9). 0.7.1 cap에서만 검게 번쩍이면 원인은 iOS 캔버스 메모리(A), 둘 다 괜찮으면 원인은 0.7.2에서 고친 투명 배경·캔버스 삭제·멈춘 사이 재렌더였다. 이 프리셋은 진단용이며 기본값으로 쓰지 않는다.
- **주의할 점:** 가로 화면 iPad의 쪽 폭 맞춤은 5,242,880 px를 넘을 수 있다. 그러면 pdf.js가 기본 캔버스 해상도를 반으로 낮추고 상세 캔버스에 기댄다. 그것이 흐려 보이면 더 큰 상한의 모바일 프리셋이 지금은 없다(필요하면 추가).
- **0.7.3 수정:** 0.7.2의 예산은 화면에 있는 것보다 작으면 pdf.js가 미리 그린 다음 쪽을 해제→재렌더하는 루프에 빠질 수 있었다(예산 2 MB 강제 시 유휴 4초에 렌더 554회, iPad *Memory saver*에서 가능). 보이는 범위 앞뒤 쪽을 보호해 고쳤다(유휴 렌더 0회). 다크 읽기 모드에서 캔버스가 아직 없는 쪽이 흰색으로 보이던 것도 고쳤다(D-39).
